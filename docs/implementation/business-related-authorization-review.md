## Q16：能否显式授权某个维度的全部取值，并包含未来新增值？

**问题：** 是否支持“经营数据、门店归属、门店全部”这种动态范围，使本企业未来新增 H 门店自动纳入？推荐支持显式动态全部，但与“选择全部现有值”的固定枚举区分，且不扩展到新类别或新必需维度。

**Subagent 决定：** 支持。界面和授权记录明确标注“全部，包含未来新增值”。“选择全部现有值”只生成当时的固定枚举快照。

**理由与边界：** 持续负责所有门店的岗位需要长期授权意图；新增 H 门店可自动纳入，但仍受本企业、已列明信息类别、账号密级及其他完整条件限制。它不包含集团级信息、新类别或未来新增必需维度；资料缺少必需属性、类别不适用该维度时不放行。显式 A/B 始终只含 A/B。

## Q17：多维度条件如何组合，避免产生本不存在的交叉权限？

**问题：** 授权中的门店 `[A,B]`、项目 `[X,Y]` 是否表示四种组合，而仅涉及 AX、BY 的资料必须保存完整范围项 `[AX,BY]`？整份读取是否要求每个实际范围项均获准，且每项不得跨授权拼接？

**Subagent 决定：** 是。同一授权条目内，同维度多值是 OR、不同维度是 AND，因此上述授权包含 AX/AY/BX/BY；只授 AX/BY 时须拆成两条授权。资料按实际完整范围项保存，不能拍平维度后凭空增加交叉组合。

**理由与边界：** 每个范围项包含归属及全部适用维度。整份 evidence 及其任一片段都要求所有实际范围项分别由完整授权覆盖；不同项可用不同授权，同一项不可拼接。结构化记录只检查自己的实际范围项；一条记录若确为多范围共有，该条也须全部覆盖。类别及账号密级条件仍须同时成立。

## Q18：单份 evidence 可否同时绑定多个授权类别？

**问题：** 推荐每文件恰好一个规范类别，授权条目仍可列多个类别；混合内容使用独立维护的组合类别或拆文件，避免多类别 OR 放宽全文权限。是否采用？

**Subagent 决定：** 一期每份 evidence 必须且只能绑定一个稳定类别 ID，按精确类别匹配。授权内多类别表示该条完整范围适用于任一列明类别。

**理由与边界：** “财务培训材料”可作为单独类别；持有培训或财务报告类别不会自动获得它。名称相似、上下级名称及检索标签均不推导权限，不新增多类别 AND 模型。admin 创建的 evidence 类别不能因同名冒充开发维护的结构化或台账 PDF 类别。

## Q19：现有系统有没有统一门店 ID？没有时能否直接使用门店名？

**代码核实：** 当前有商户号字段，但没有所有业务都必填、共用的统一门店 ID。经营/菜品销售分区优先用商户号，缺失时退回门店名；`StructuredPartition.merchantId` 可为空。VIP 保存商户号、储值门店名称、开卡门店名称，但没有为两个门店分别定义统一 ID。台账按门店名关联，PDF 按企业、门店名哈希和日期标识；检疫照片当前按单号关联，没有独立门店字段。以上是本地代码/数据结构核实，不代表已检查线上每条记录的商户号完整性。

**当前规则（按用户条件修订）：** 既然不存在贯穿业务的稳定门店 ID，目标业务权限以本企业内的门店名作为门店身份，按名称精确匹配。不同名称按不同门店处理，即使看起来相似也不自动归并；不建设名称相似度检查、模糊匹配或自动别名推断。

**理由与边界：** “陆家嘴店”和“陆家嘴一店”是两个不同门店身份，不因相似而暂停导入请人判断；授权一个名称不会自动授予另一个。现有商户号可保留为来源字段/现行分区键，但不能让一个业务按编号、另一个按名称产生两套授权语义；后续实施须衔接现行分区存储。对需要门店授权的类别，必需名称为空仍属于字段缺失，不等于名称相似。会员数据已按 Q20 改为集团级，门店字段仅按导入数据契约处理，不再用于权限归属判断。原草案的新增统一编号、必备别名映射以及未知名称一律整次暂不发布，不作为已确定要求。

**代码依据：** `packages/domain/src/structured-partitions.ts` 的 `partitionStoreIdentity`、`packages/db/prisma/schema.prisma` 的 `StructuredPartition`/`QuarantineCertificate`/`LedgerPdfPartition`、`packages/domain/src/structured-registry.ts` 的 VIP 和台账字段、`packages/ledger-archive/src/keys.ts`。现行经营/菜品名称退回路径有去首尾空格、空白规范化及 ASCII 小写处理；台账/PDF 使用精确名称。这些现行差异不应被误称为已经统一，实施时须统一授权名称比较口径，不引入相似匹配。

## Q20：会员数据是否需要按门店分配读取权限？

**问题：** 一名会员在 B 店开卡、在 A 店储值，读取对应会员数据是否需要 A 店或 B 店权限？

**当前规则（用户明确确认）：** 会员数据属于本企业集团级数据，不按门店限制读取。获得会员类别的集团级读取权限、且满足类别密级的员工，可以读取本企业全部会员数据；不需要储值门店或开卡门店授权。撤回原来要求同时拥有两店权限的草案。

**实际例子：** 员工有集团级会员数据权限、密级也足够，即使没有 A 店或 B 店的经营数据权限，也能查看该会员记录。员工只有 A 店经营数据权限、没有会员数据权限，则不能查看该记录。员工可以按储值门店筛选会员数据，筛选只用于查找，不改变授权范围。会员数据原文件自动继承该集团级类别权限和密级，不追加两店授权条件。集团级始终限本企业，不跨企业。

## Q21：检疫证明照片如何独立定类、定密和定业务归属？

**问题：** 现有照片可先于台账上传、仅按单号关联。推荐固定“检疫证明”类别、企业内统一定密、admin 上传时显式声明完整业务范围；单号仅关联，范围冲突须修正而非悄悄改权限。是否采用？

**当前规则（用户修订）：** 检疫证明采用开发维护的固定类别，企业 admin 配置类别统一密级。每张检疫照片必须且只能归属一家门店；每份台账 PDF 也必须且只能归属一家门店。不支持 A/B 共有照片或跨店单份 PDF。

**理由与边界：** 原草案把 evidence 的多门店共有情形误延伸至检疫照片，该假设撤回。照片、关联台账和生成 PDF 的所属门店须一致，不能只凭单号忽略门店；员工读取 PDF 按成品类别权限检查，不要求单独的照片读取权。多份 PDF 打包不改变每份 PDF 的单门店属性，也不构成一份跨店 PDF。

## Q22：PDF 独立授权后，是否还依赖上游资料的有效性？

**问题：** 推荐上游权限和密级变化不影响 PDF，但来源归档、无效或归属冲突仍使产物过时；普通供应商内容更新沿用不自动刷新历史 PDF 的既有规则。是否采用？

**Subagent 决定：** 区分授权与生命周期。PDF 只按自身类别、范围和当前类别密级读取；不再比较上游密级或员工上游授权，也不因此重生成。实际来源有效性及输出范围契约仍必须成立。

**用户确认与补充：** 仅修改检疫照片的读取授权或密级，不改变相关旧 PDF 的业务授权、门店范围或密级，也不因此让 PDF 失效或重新生成。PDF 继续按其自身当前权限读取。

检疫照片的内容被修正、照片被替换、撤下或归档后，受影响的旧 PDF 应随之失效，系统不再提供该旧 PDF 下载。每日 PDF 巡检自动按最新有效照片重新生成 PDF：已撤下的照片不再放入，被替换的使用当前有效照片。新 PDF 成功生成并通过检查后才提供下载，不要求用户手动补图才能触发巡检重做。若还有其他实际生成错误，则继续显示未就绪，不能退回已失效旧版。这里的失效和重生成不是权限继承，新 PDF 仍按 PDF 自身的类别权限管理。

**理由与边界：** 照片从 A 店纠正为 B 店时，A 店旧 PDF 同样失效，巡检须按正确门店关联重做。供应商普通内容更新不自动刷新历史 PDF 的原规则仍保留。已签发链接仍按此前用户确认保留原有效期；失效后的系统下载请求不再拿到旧版，并不追溯撤回外部已签发链接。这里只确认目标行为；代码已有每日巡检与自动修复任务，不据此声称新权限模型已实现或线上巡检已核验。

**具体例子（区分照片权限变化与内容/有效性变化）：**

| 情况                                                               | 草案下的结果                                                         |
| ------------------------------------------------------------------ | -------------------------------------------------------------------- |
| 员工有 A 店 PDF 权限且密级够，没有供应商名单或检疫照片的独立读取权 | 可以读取 A 店 PDF，包括模板中已纳入的来源内容                        |
| 检疫照片类别从 1 级升至 3 级，PDF 类别仍为 1 级                    | 原本能读该 PDF 的员工仍可读，不因此重生成                            |
| 发现 PDF 使用了错误照片，管理员将这张照片归档撤下                  | 旧 PDF 失效；每日巡检自动重做，不再放入这张照片；新 PDF 就绪后可下载 |
| A 店 PDF 所引用的照片被纠正为 B 店照片                             | A 店旧 PDF 失效；巡检按正确的门店和照片关联重新生成                  |
| 供应商仅正常更新联系电话                                           | 不自动重做历史 PDF；下次实际重新生成时使用当前目录信息               |

以上旧 PDF 失效均不撤回已签发链接；旧链接继续按原有效期使用。

## Q23：没有正文读取权的 admin，能否查看管理信息和处理状态？

**问题：** 当前部分处理状态要求上传者本人且密级够，可能阻断已获管理权的 admin。推荐设置独立管理视图，允许必要元数据和安全错误，不开放正文或文件。是否采用？

**Subagent 决定：** 有效 admin 在本企业可查看权限维护和处理跟踪所需账号、类别、维度、资料标识、标题、文件名、权限属性、状态及脱敏错误，不受普通业务授权/账号密级限制；修改仍须遵守各资料契约。

**用户明确补充：** 管理员能查看本企业所有账号的完整业务授权与密级，包括自己、其他管理员和普通员工；不仅是允许增删改，还必须允许查询这些权限配置。

**理由与边界：** 这是管理角色权力，不是上传者内容特权。错误可含结构化码、字段名、位置、管理引用，不回传原始行、单元格值或含内容的底层异常；不自动返回正文、片段、照片、原文件或链接。普通读取元数据/计数/覆盖仍受授权限制，上传者身份不单独授予普通状态读取权。

## Q24：原文件怎样自动继承成功解析出的数据权限？

**问题：** 文件成功解析出的结构化数据属于 A，另有内容未识别，整份原文件应该按什么权限读取？如果分别解析出属于 A、B 的数据，又该如何读取原文件？

**当前规则（用户明确确认）：** 文件成功解析出的结构化数据，由业务逻辑得到的权限限制，自动成为原文件的读取限制，包括信息类别、门店等业务范围以及适用密级；不限于门店这一种属性。未识别内容跟随整份原文件的权限，不另外分析、定权，也不因此禁止原件下载。无需管理员额外声明或确认整份原文件的权限范围。

**实际例子：**

- 只解析出属于 A 的数据，其他部分未识别：整份原文件（包括未识别部分）按 A 的权限读取；满足 A 全部读取条件的员工，可以读取 A 的结构化数据，也可以下载整份原文件。
- 分别解析出属于 A、B 的数据：下载原文件必须同时满足 A 和 B 的全部读取条件；只满足 A 的员工仍可读取 A 的结构化数据，不能下载整份原文件。
- 系统只解析出 A，未识别的另一张表即使实际写有 B，也不会被系统另外赋予 B 权限：它跟随原文件按 A 管理，不引入额外扫描或人工声明要求。

**理由与边界：** 原文件取自该文件实际解析出的全部数据权限要求，不能只根据当前请求者看得到的部分确定；条件同时成立，不是任意满足一项即可。原文件随这些数据的当前权限规则校验，而不是在导入时冻结旧权限。撤回原草案的完整解析覆盖清单门槛，也撤回后续“管理员确认整份文件范围”的建议；这个问题已经确认，不再保留为待定。原始配送台账仍遵守此前只供内部生成的特殊规则，PDF 仍按已确认的独立类别权限读取；本规则不另外开放被明确关闭的读取入口。

## Q25：请求部分越权时，返回子集还是整次拒绝？

**问题：** 推荐普通查询只返回授权范围，明确完整交付则任何目标不可用都拒绝，不静默缩小；如何划清边界？

**Subagent 决定：** 接口明确区分“授权范围内查询”和“明确目标完整交付”，不能仅凭参数里是否出现门店列表判断。查询先限权再排序、聚合、计数、分页；查询结果导出沿用同一口径。

**理由与边界：** A/B 业务筛选只是授权数据内的谓词，不承诺返回未授权 B。明确要求文件 F、分区 A/B 或已确认清单打包时，任一目标无权或不可交付，不得将剩余子集当作成功；排除目标需调用方重新选择。正常查询计算仍只针对授权数据。错误提示按用户对 Q29 的修订，可说明受限资料名称、简要概述或解释失败所需的汇总信息；不再强制将无权与不存在统一成模糊错误，但错误提示不提供受限正文、数据明细或下载能力。

## Q26：权限变化后，旧查询游标和异步打包任务如何处理？

**问题：** 权限变化时，如何处理旧查询翻页和已经提交的打包任务？用户认为制作期间撤权概率低，不应为此增加大量中途撤销逻辑或让打包任务失败。

**当前规则（按用户要求简化）：** 查询翻页仍绑定企业、账号及权限规则，相关规则变化后重新查询。打包提交时校验权限并固定清单；后台不持续监听或重复执行发起人的业务读取授权，不因其业务授权/密级变化中止或把任务标记失败。有效本人可查看任务进度。申请新的下载链接时复用当前读取权限检查；无权只拒绝提供链接，不把成功任务改成失败。

**理由与边界：** 不新建权限变更监听、批量扫描取消任务或特殊撤权重试机制。扩权/撤权均不扩缩清单；来源归档、文件损坏、PDF 失效等实际内容/生命周期问题仍按原完整性规则处理。任务状态只返回进度等必要信息，不代替正文/清单内容/下载的授权；账号须当前有效、同企业且为任务本人。其他 admin 可查看管理状态，但不能接管普通下载。原有链接按原 TTL 有效；已正常受理的上传不因上传者普通读取权限变化取消。

## Q27：新账号，尤其 admin，是否默认获得全部业务读取权限？

**问题：** 推荐新账号业务卡默认空、开户可显式授予；admin 只有创建时默认最高密级和管理权，角色切换不自动改密级或 grant。是否采用？

**Subagent 决定：** 新 employee/admin 均无隐式业务授权，显式初始 grant 须留痕。创建为 admin 默认最高等级，employee 需显式指定 0–3；角色、岗位、企业成员身份和上传者身份都不推导业务范围。

**用户确认与补充：** 同意上述规则。开发者创建 admin 时可以同时显式配置初始业务授权并留痕；“默认空”只表示未指定授权时为空，不要求先创建空账号、再由 admin 登录自授。

**理由与边界：** 新 admin 可管理必要元数据、显式给自己授权，但无 grant 时不能普通读取内容。角色切换不自动修改既有密级或 grant；降为 employee 失去管理权，但已有业务授权不自动撤销。开户、角色切换保持开发/运维边界，本次不新增 admin 升任其他 admin 或重置密码能力。

## Q28：历史上传者降为 employee 后，是否仍能归档已发布照片？

**问题：** 当前按资料 ID 归档照片允许原上传者或 admin。推荐已发布资料归档统一要求当前 admin，仅保留未完成上传的本人清理例外；是否采用？

**Subagent 决定：** 现有已发布业务资料归档统一要求同企业有效 admin，不受普通读取权限限制；撤销历史上传者非 admin 仍可归档的特权，按资料 ID 与单号遵守相同边界。

**理由与边界：** 当前有效账号可取消自己未完成的上传会话，即使已非 admin，但仅清理会话专属未发布资源；不能撤销已受理正常处理、影响已发布或被引用资源。停用账号无自助取消权。本决定不新增通用删除或结构化行编辑功能。

## Q29：员工能看到怎样的权限名片和类别目录？

**问题：** 推荐实时 self-only 权限名片，展示自己的配置；目录不成为未授权资料探测入口。是否采用？

**Subagent 决定：** 员工可实时只读查看本人密级、完整 grant、固定/动态范围语义，以及已获授类别的规则和维度；即使等级不足或配置未补齐，也可理解自己的配置及受限原因。

**用户确认与修订：** 整体同意本人权限名片；不要求错误提示隐藏所有受限信息的名称或概述、汇总。例如可以直接说“你没有查看 A 店财务报告的权限”，无需含糊成“资源不可用”。

**理由与边界：** 固定范围展示其枚举，动态全部明确包括未来值。目录仍以本人授权范围为主，此修订不新增企业全量目录浏览功能。错误提示可显示资料名称及解释失败所需的概述、汇总，不直接返回受限正文、明细或下载链接；正常业务查询仍限获准数据。admin 目录按 Q23。

## Q30：一期通过哪些入口交付权限管理？

**问题：** 推荐受控 HTTP 管理 API 为权威，官方 MCP 提供 admin 工具和本人权限名片，完整管理网页不作为必要范围；是否采用？

**Subagent 决定：** 采用。覆盖授权增改撤、账号密级、evidence 类别/维度目录及映射、资料权限属性、类别统一密级和必要管理查询。

**理由与边界：** 后端每次验证当前有效 admin 与同企业目标；写操作原子校验、审计操作者及前后值，并拒绝过期版本覆盖。MCP 不另设绕过 API 的逻辑。开户、角色、密码保留运维边界；内部后台处理使用明确内部权限，不能伪装成员工 admin。完整 Web 管理界面不作为本轮必要交付。

资料权限属性维护遵守对应资料类型的规则：evidence 可以由管理员维护整份属性，结构化原文件则按 Q24 自动继承，不增加独立的原件业务范围或密级编辑入口。

## Q31：类别或门店改名、停用后，历史访问与补录怎么办？

**问题：** 推荐稳定 ID 不复用，改名不改权限；停止新增与撤销历史访问分开，同时保留明确的历史补录路径。如何收口目录生命周期？

**Subagent 决定：** 采用“正常使用／停止新增但保留历史”两态。已被引用的对象不能硬删，停用不撤销既有资料访问，固定授权与动态全部仍覆盖该历史对象。

**理由与边界：** 停用对象不作为普通新声明的默认选项；admin 可显式执行历史补录/纠错，记录理由并完整校验，有业务日期时检查历史语义。停用类别仅能使用仍受支持的处理能力。撤销历史访问须改授权、资料权限或归档，不能靠停用目录项隐式完成。

**Q19 修订的影响：** 门店以名称作为业务身份后，“门店改名只改展示且所有授权自动沿用”不能直接适用。不同名称按不同身份，不自动迁移资料或授权；如果以后需要门店正式更名并迁移历史关系，应作为明确的迁移操作另行定义。类别及其他具有独立稳定 ID 的目录项仍按原规则。

## Q32：缺少初始权限配置的数据，能否使用默认值发布？

**问题：** 推荐 evidence 显式声明完整属性，固定类别先配置企业密级及所需维度、映射；缺失不自动当作 0/3 级或集团级。是否采用？

**Subagent 决定：** 采用。允许准备数据，完整配置并通过校验后才发布；未准备好不得进入普通查询、下载或派生交付，admin 可在管理视图补齐缺项。

**理由与边界：** 新导入不替换既有且符合当前规则的有效版本；新必需维度正式启用后，旧版本也须满足，不能借历史有效状态绕过。配置类别、完成发布均不自动授予员工访问权；最高密级同样不能弥补业务范围缺失。

## Q33：旧企业怎样迁移，失败后能否回退旧权限放行？

**问题：** 推荐按企业准备、显式补齐确认、原子启用；不推测旧资料分类或默认全量授权，切换后不做旧/新任一通过的兼容放行。如何定义切换和回退？

**Subagent 决定：** 采用。准备期明确仍使用现行规则；新类别配置和初始授权由 admin 确认。启用后所有入口只认新规则，缺项拒绝，旧游标失效，下载任务复核，既有链接保留原 TTL。

**理由与边界：** 切换前可撤销未生效配置；切换后技术回退必须保留新授权检查，不能保障时暂停受影响读取。恢复旧配置须作为经当前契约校验并审计的新变更，不能自动恢复已撤销权限。迁移保留原始资料；本设计不构成部署或真实数据迁移授权。

## Q34：集团供应商资料怎样合法进入门店 PDF？

**问题：** 简单要求所有来源与 PDF 范围相同会挡住现有集团供应商资料的使用。推荐开发按来源类型定义必要字段和范围转换，照片则保留完整归属校验；是否采用？

**Subagent 决定（按 Q21 用户修订同步）：** 采用明确的来源类型转换契约：台账属于 PDF 的唯一门店；集团供应商目录按单据供应商精确匹配，只投影模板所需的已定义字段；检疫照片也必须归属该同一门店，不支持跨店共有照片。

**理由与边界：** 不携带其他供应商记录，不授予员工上游查询权。集团级也不免除其他适用维度；新增维度或来源类型尚无明确转换规则时阻止发布，不能静默忽略或将独立 PDF 规则推广到任意导出。

## Q35：整体复核还有阻止设计闭合的核心缺口吗？

**问题：** 对用户已确认目标和 Q16–Q34 作整体复核，只指出最重要的一项业务未决，避免把实现细节当作新增业务问题。

**Subagent 结论：** 还有一项：一期现有结构化数据集到规范类别及初始归属的统一映射没有明确固定。例如“菜品销售”和“菜品目录”是否独立授权，不能由实现者自行解释。

**理由与边界：** 这是当时的复核结论。类别映射由 Q36 补齐，会员规则后经用户改为集团级，最新结果以正式设计为准。

## Q36：一期现有资料怎样映射到独立类别和归属？

**问题：** 推荐经营、菜品销售、会员储值、菜品基础目录、供应商名单分别独立成类；明确集团/门店归属，原始台账仅内部使用，照片及 PDF 保持独立类别。是否采用统一接入契约？

**Subagent 决定：** 采用下表，各类别独立授权；名称相近不产生互授。

| 数据集／资料       | 规范类别     | 一期初始归属及交付边界       |
| ------------------ | ------------ | ---------------------------- |
| `business`         | 经营数据     | 记录所属门店                 |
| `dishes`           | 菜品销售数据 | 记录所属门店                 |
| `vip`              | 会员数据     | 集团级，不按门店限制读取     |
| `dish_catalog`     | 菜品基础目录 | 显式集团级                   |
| `supplier_catalog` | 供应商名单   | 显式集团级                   |
| `delivery_ledger`  | 原始配送台账 | 单据所属门店，仅内部生成输入 |
| 检疫照片           | 检疫证明     | 必须且只能归属一家门店       |
| 台账 PDF           | 台账 PDF     | 必须且只能归属一家门店       |

**理由与边界：** 固定类别由企业 admin 配置统一密级；evidence 仍由 admin 自定义类别、逐文件定密。原始台账不进入员工可授予读取类别，不开放明细、原件或汇总。集团级是明确接入语义，不从缺少字段推导；目录将来改按门店划分须新契约及迁移。会员储值类别名称不替代金额字段业务口径的验证。

**“各自独立”的解释：** 指检疫证明和台账 PDF 是两个可以分别授予的读取类别。例如员工只有“A 店台账 PDF”授权，可以看该成品 PDF，包括已排入 PDF 的照片，但不能单独下载检疫照片原件；只有“A 店检疫证明”授权则不自动获得台账 PDF 权限。它不表示 PDF 生成不再使用照片，也不表示允许多门店归属。两类各有本企业的统一密级，PDF 不自动继承照片密级。

## 结构化数据与原文件：统一权限原则

这条主线遵循用户确认的规则：先按业务规则确定文件解析出的结构化数据受哪些权限限制，整份原文件自动受到所有这些限制。未识别内容随原文件管理，不再另建一套原件权限。

| 用户实际遇到的情况                                   | 一致的处理方式                                                                  |
| ---------------------------------------------------- | ------------------------------------------------------------------------------- |
| 文件只解析出 A 店经营数据，其他表没有识别            | 满足 A 店经营数据的全部读取条件，就能读这些数据并下载完整原文件，包括未识别部分 |
| 文件分别解析出 A 店、B 店经营数据，员工只有 A 店权限 | 员工可查询或导出 A 店数据；下载完整原文件还须满足 B 店权限                      |
| 经营数据类别的密级从 1 级改为 3 级，员工只有 2 级    | 后续既不能读取经营数据，也不能申请下载其原文件；原文件不继续使用旧的 1 级       |
| 员工后来失去 B 店权限，原件解析出了 A、B 两店数据    | 后续仍可读 A 店数据，但不能申请下载整个原件；已经签发的链接仍保留原有效期       |
| 原件解析出的数据属于集团级供应商名单                 | 原件跟随供应商名单的集团归属、类别密级和其他适用条件，不额外要求或推导门店权限  |
| 某类别以后新增了必需业务条件，并正式启用             | 结构化数据按新条件检查，原文件也随之检查；不靠下载原文件绕过                    |

多条授权能分别完整覆盖所需范围时，可以共同满足整份原件要求；不能把某条授权的类别和另一条授权的门店条件拆开拼接。普通查询、分区下载和只包含获准数据的导出，仍按各自实际包含的数据检查。

原件的当前权限来自解析出的全部数据，不保留另一套上传时人工设置的业务范围或密级。这也意味着迁移、管理入口和权限修改不能只更新结构化查询，却让原件下载沿用旧条件。现行代码还存在按上传文件密级检查原件的实现，后续实施必须替换；本次只是目标设计核对。

原件规则仅作用于实际保留的原件，不新增存储能力。ADR 0026 中经营/菜品销售导入后只保留当前标准化分区、删除临时来源文件的边界保持；本文的跨店原件例子描述授权条件，不承诺为这些已不保留原件的数据集新增 Excel 下载。

以下是已经明确的不同资料处理规则，不与上述结构化原文件原则混用：

- 普通文档（evidence）由管理员给整份文档设置类别、范围和密级，搜索出来的段落沿用整份文档权限；这里并没有先从文件解析出可独立授权的结构化行。
- 台账 PDF 是系统生成的独立业务类别，不是上传的台账 Excel 原件。看 PDF 的权限不会反向开放供应商名单、检疫照片或原始台账，来源权限也不会自动传给 PDF。
- 原始配送台账已明确仅供内部生成使用，不向员工开放明细、汇总或原文件下载。自动确定其权限不等于重新增加一个已决定关闭的下载入口。

## 本轮收口与实施边界
