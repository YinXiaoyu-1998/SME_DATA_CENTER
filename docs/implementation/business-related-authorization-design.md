# 业务权限与原文件权限设计

更新：2026-10-13。状态：当前最终权限契约，已在 main 实现；每个租户按准备/激活状态执行。

本文是当前权限模型的权威说明。后台打包按固定清单制作，领取链接时检查当前权限；管理员可以管理本企业所有账号的权限。代码/部署状态见当前实施计划与 staging-readiness.md，真实企业补齐和激活仍须单独授权。

面向非技术使用者的例子见 [使用说明](business-related-authorization-guide.md)，用户要求保留的逐项问答及修订见 [设计问答](business-related-authorization-review.md)。问答只保留决策历史，当前规则以本文为准。

## 1. 目标与边界

SMEDC 继续作为员工自有 agent、CLI、MCP 和 API 的资料/数据服务，不增加员工聊天助手、报表生成器、看板或 Skill 执行器。

enabled 模式读取要求“同组织、账号有效、信息类别和全部适用业务条件获准、密级足够”。管理员负责管理权限，但管理员角色、上传者身份都不直接赋予普通正文读取权。

本设计覆盖普通文档搜索、结构化行查询、当前分区下载、保留原件下载、检疫照片、台账 PDF、下载任务、本人权限查看及管理操作。所有非健康接口继续执行服务端授权，客户端隐藏按钮、缓存角色或提示文字不能代替鉴权。

本设计不改变当前文件保存方式：`business`/`dishes` 按 [ADR 0026](../adr/0026-business-dishes-current-oss-partitions.md) 只保留标准化当前分区，临时来源文件仍删除。原文件自动继承权限的规则作用于实际保留的原件，不新增这两个数据集的原始 Excel 留存或下载。企业内现有数据企业标识及组织隔离保留，不能因门店同名跨企业合并数据。

## 2. 账号、资料类别与业务范围

### 2.1 账号及管理员

账号保留 `admin`/`employee` 功能角色、有效/停用状态和统一 0–3 级账号密级，并持有多条业务授权。不同授权不分别设置账号密级。

- 新账号没有隐式业务授权。开发者开户时可显式配置初始授权并审计；未指定才为空。
- 创建为 admin 时密级默认 3，之后可降低或提高，包括管理员修改自己；系统不自动恢复最高级。
- employee 创建时明确指定密级。既有账号切换角色不自动修改已有密级或业务授权。
- 当前有效 admin 可以查看、新增、修改、撤销本企业所有账号的业务授权，并查看、修改其密级，目标包括本人、其他 admin 和 employee。管理员能授予自己尚未拥有的业务权限。
- 管理员查看别人完整权限配置不等于读取别人可见的业务内容。普通员工只能查看自己的权限名片。
- 开户、角色变更和密码管理保留开发/运维边界，本次不扩展为普通管理员的账号凭证管理功能。

### 2.2 一期类别与归属

| 资料                           | 类别维护者         | 归属及普通读取边界                               | 密级来源                         |
| ------------------------------ | ------------------ | ------------------------------------------------ | -------------------------------- |
| `business` 经营数据            | 开发接入           | 门店，读取获准当前分区                           | 企业类别统一密级                 |
| `dishes` 菜品销售数据          | 开发接入           | 门店，与菜品基础目录独立                         | 企业类别统一密级                 |
| `vip` 会员数据                 | 开发接入           | 集团级，不按储值/开卡门店授权                    | 企业类别统一密级                 |
| `dish_catalog` 菜品基础目录    | 开发接入           | 集团级                                           | 企业类别统一密级                 |
| `cost_cards` 成本卡目录        | 开发接入           | 集团级，明细通过本地 CSV                         | 企业类别统一密级                 |
| `store_reviews` 店铺评价       | 开发接入           | 精确单门店，当前授权结构化行                     | 企业类别统一密级                 |
| `supplier_catalog` 供应商名单  | 开发接入           | 集团级                                           | 企业类别统一密级                 |

类别统一密级由本企业 admin 配置，作用于全部新旧资料，不按导入批次或供应商记录分别定密。会员门店字段保留业务查询作用，但不构成读取限制。集团级仅限本企业，并不等于所有门店；若类别另有明确业务维度，集团级仍需满足那些条件。

evidence 是处理方式，不是业务类别。类别名称、标签、名字中的上下级关系不产生权限继承；自定义 evidence 类别不能冒充固定结构化或 PDF 类别。新类别不自动授予员工，也不自动增加文件解析能力。

### 2.3 门店身份与其他维度

当前代码仅部分路径支持可空商户号，台账/PDF 按门店名工作，没有贯穿所有路径的必填门店 ID。授权在同一企业范围内按门店名称精确匹配，不做相似度检查、模糊匹配或自动别名合并。现有商户号及物理分区键可保留，但不能形成与门店名并行、可额外放行的第二套授权规则。

授权比较使用统一的、持久化的门店名称值；既有读取器的格式清理与历史键须在迁移时明确衔接，不借此合并不同业务名称。例如“陆家嘴店”和“陆家嘴一店”始终不同。名称为空与名称不同是两种情况，适用门店权限的数据不能把缺失名称当作集团级。

evidence 的业务维度及取值由 admin 显式维护；结构化类别新增维度由开发与 admin 明确属性来源、适用范围和处理规则后接入。同一含义的维度共用定义，不根据名称相似推断同义。

## 3. 统一读取判定

### 3.1 授权条目与实际资料范围

每条授权绑定一个或多个明确类别、归属类型，以及全部适用维度的允许取值。同维度多值表示任选其一，不同维度必须同时满足；多个类别仅在共同适用全部条件时才允许放入同一条授权。不适用的条件应拒绝配置，不能在读取时悄悄忽略。

资料保存实际完整范围项，而非把各维度拍平成独立值集合。例如资料实际涉及 `A店/X项目` 和 `B店/Y项目`，不能凭空扩成四种组合。共有的单条记录及整份 evidence 须覆盖其所有实际范围项。

对一份可独立读取的资料，条件为：

1. 当前账号有效，资料、授权、账号属于同一组织及适用的现有企业边界。
2. 资料当前有效，所需权限属性已完整确定。
3. 账号密级不低于该资料当前要求的密级。
4. 资料每一个实际范围项，都能被至少一条完整业务授权覆盖；这条授权同时包含该类别、归属及全部适用维度条件。

不同范围项可由不同授权覆盖；同一项不能把一条授权的类别与另一条授权的门店拼接。无匹配授权不放行，不引入显式拒绝条目、角色隐式继承或额外逐字段权限体系。

### 3.2 动态全部与固定枚举

固定 A/B 只包括 A/B。“全部，包含未来新增值”必须显式选择，仅覆盖已列明类别、归属和维度，不包含新类别、集团级或未来新增必需维度。关闭但保留历史资料的门店仍在相应固定授权或动态全部范围内。

### 3.3 当前权限与请求边界

后续普通读取和领取新下载链接，使用服务端当前账号和权限配置，不等重新登录。每次请求复用统一判定逻辑，不另建持续监听所有活跃请求的权限撤销系统。

查询游标绑定组织、账号及权限规则；相关规则变化后要求重新查询。已签发对象存储下载链接保留原 TTL，包括原件链接已有的 24 小时，不新增提前撤回或缩短有效期机制。

## 4. 结构化数据与保留原件

业务规则确定结构化数据的类别、业务范围及当前类别密级；保留的原文件自动受到该文件成功解析出的全部数据权限限制。不能另设一套原件业务范围、上传批次旧密级或管理员确认步骤。

- 只成功解析出 A，其他部分未识别：整份原件连同未识别内容按 A 管；满足 A 全部条件即可读取 A 数据和下载完整原件。
- 分别解析出 A、B：完整原件要求同时满足 A、B 全部条件；只满足 A 仍可查询/导出 A 数据。
- 存在不同类别或不同维度时，同样检查每部分的完整当前要求，不能只取门店列表或仅检查一个最高密级就省略类别条件。
- 未识别内容不另行扫描、分类或额外定权；不要求解析器证明整份文件所有内容已覆盖。正常导入校验仍适用，导入失败或尚无可确定授权的数据不能被解释成无条件可读。
- 原件权限来源必须覆盖该原件实际解析出的全部数据，不能只取当前调用人看得到的行。类别密级或相关数据权限变更后，原件下一次读取跟随新规则。

实现保留可追溯的导入数据与原件关联，并从权威权限记录求得约束；这不是要求建立未解析内容的权限清单。当前分区、标准化结果和查询导出按实际包含的数据授权，不因无法下载整个来源文件就阻止获准子集读取。

`business`/`dishes` 不恢复通用逐行或服务端聚合查询，不新增来源保留；它们在现有分区目录、manifest、提取及打包路径实施门店和类别权限。原始配送台账仍不开放员工查询、汇总和原件，通用原件继承规则不能重新打开这些入口。

## 5. 普通文档、检疫照片与台账 PDF

### 5.1 evidence 普通文档

上传时 admin 明确选择已有类别、完整范围及逐文件密级。每份文件恰好一个类别；混合主题可使用显式组合类别或拆文件，不因持有某个相似类别而放行全文。

整份文件及每个搜索段落继承相同完整要求。例如 B/C 共有文档，即使某段只提 B，也要覆盖 B/C。admin 可在上传后修改整份属性，并审计前后值；片段不单独改权限。搜索、引用、下载一致使用当前权威权限，旧索引或缓存不能继续按旧条件放行；检索/重排不得把未获准内容交给调用者或其内容处理环节。

### 5.2 单门店照片与独立 PDF

检疫照片可先于台账上传，但须明确唯一门店；单号用于业务关联，不单独授予权限。照片、台账及 PDF 的所属门店须一致，不支持 A/B 共有照片或单份跨店 PDF。多份单门店 PDF 可以按获准清单打包。

PDF 独立使用其类别、门店和类别密级。员工有 PDF 权限即可读成品，包括其中照片和供应商字段，无须分别拥有来源读取权；它不反向授予照片原件、供应商目录或原始台账权限。

来源组合契约由开发维护：本门店台账、单据准确匹配供应商的模板必要字段、同门店检疫照片。集团供应商目录允许按此规则向门店 PDF 提供对应字段；其他适用业务维度不因集团归属被忽略。新增维度/来源没有明确转换规则时，不默认放行生成。

### 5.3 权限变化和内容变化分开

单纯修改照片或其他来源的读取授权、密级，不改变 PDF 权限、不使 PDF 失效、不触发重生成。生成指纹、来源当前性及失效逻辑必须区分内容/业务关联变化和仅权限变化，不能继续把来源密级变更当作 PDF 失效原因。

照片内容修正、替换、撤下、归档或门店关联纠正导致旧成品来源不再正确时，旧 PDF 失效，系统不再提供旧版新下载链接。每日巡检按最新有效来源自动重做；撤下照片不再纳入，替换照片用当前有效版本，不要求必须补图才允许巡检重做。新版正常完成后可下载，不能把生成失败回退成下载失效旧版。

实际引用台账/来源无效仍须处理其成品有效性。供应商普通内容更新沿用既有不自动刷新历史 PDF 的规则，实际重做使用当前目录。已签发链接仍保留原 TTL。以上不改变 PDF 自身独立权限。

## 6. 查询、下载与简化的后台打包

### 6.1 查询范围和完整目标

普通查询先授权再搜索、筛选、排序、聚合、计数、分页；结果及普通导出只代表获准范围。参数出现门店列表本身不等于承诺完整交付该列表。

明确原件、指定文件清单或完整分区清单下载时，全部目标须可读取、可下载，不能默默删除无权项后报告完整成功。错误可明确指出资料名称或说明失败所需的概述/汇总，但不能借错误返回正文、原始明细或下载能力。

### 6.2 打包检查位置

采用“提交时授权、固定清单制作、领取链接时授权”，不引入制作期间的实时权限监听或撤权任务取消机制。

| 阶段         | 检查与行为                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 提交打包     | 当前有效账号、同企业和完整清单读取权限；固定实际目标、身份及内容引用，不只保存将来会扩张的查询条件                                                        |
| 后台制作     | 内部任务按已受理清单执行；不重复检查发起人业务授权/密级，不因这些条件中途变化终结任务；既有文件校验、来源有效性、租约、超时、重试、大小限制和清理继续适用 |
| 查看任务状态 | 当前账号有效、同企业、任务本人；仅返回必要进度/结果状态，不附正文、内容明细或下载链接。admin 可走明确管理查询                                             |
| 领取新链接   | 包正常完成且未过期、来源仍有效、本人当前可读取清单全部内容；不足则拒绝链接，不把制作成功改为制作失败                                                      |
| 已签发链接   | 按既有 TTL 使用，不因随后撤权提前失效                                                                                                                     |

**例子：** 小王提交 A/B 包，制作第二分钟失去 B 权限，任务仍可五分钟后正常完成；领取新链接时缺 B 权限而被拒绝，任务仍是已完成。恢复权限且包仍有效时可再领取，或另建仅 A 的包。期间扩权也不向旧包新增文件。

其他管理员不能接管这个人的普通下载，可按自身授权另建任务。文件损坏、来源归档或 PDF 失效造成的实际不可用，不属于“仅发起人权限变化”，继续按现有完整性规则处理；不生成少文件的成功包。

### 6.3 复杂度边界

发起人读取权在提交和领取新链接时检查；制作过程保留文件/来源有效性、租约、超时、重试、大小和完整性约束。权限变化导致的链接拒绝不改变已完成任务状态。

不增加授权变更订阅、遍历活跃任务、按文件轮询账号权限、撤权专属重试或更短链接 TTL；使用统一读取判定。

## 7. 管理、状态与资料生命周期

管理能力通过统一 HTTP API、官方 MCP 及企业专属最小权限 UI 提供。覆盖所有账号权限查询/增改撤、密级配置、evidence 类别/维度维护、适用资料属性修改及必要处理状态。API 每次检查当前 admin 和目标组织，禁止跨企业；MCP 不维护可绕过服务端的平行授权。

权限写操作原子校验，记录操作者、目标、前后值及结果，并使用版本条件拒绝过期配置覆盖。只查询权限不要求操作者自己具备这些业务读取权限。结构化原件属性自动继承，不能通过管理入口独立改成更宽。

admin 可查看管理需要的账号、资料名称、权限配置、处理状态和安全错误，但不自动返回正文、行、照片或原件链接。员工本人权限名片实时显示密级、完整授权和已获授类别规则；错误可以说明缺少哪个资料的权限，不强制隐藏存在性。此能力不新增全企业未授权资料目录浏览。

已发布资料的现有归档操作统一要求当前同组织有效 admin，撤销历史上传者降为 employee 后仍能归档的特权。有效账号可取消自己尚未完成的上传，只处理会话专属未发布资源，不撤销已受理处理或影响已发布/被引用资料。停用账号无自助取消权。

管理员授权上传后，后台处理以内部工作身份完成，不因上传者普通读取权变化取消，不伪装成管理员账号。开户和其他特权操作继续各自校验当前身份。

## 8. 配置准备、目录维护与迁移

已接入的可读取固定类别由 admin 明确企业密级；内部 delivery_ledger 类别不要求管理员设置读取密级。各资料必需业务属性完整后才可发布读取，不以默认 0、最高级或集团归属代替缺项。evidence 逐份属性显式声明。类别配置完成不自动产生员工授权；新导入未就绪不替换仍符合当前规则的有效版本。

新增必需业务维度按“准备、明确补齐资料及授权、启用”处理。启用后缺项不放行，包括旧资料和原文件。门店新名称按精确名称处理，不因与旧名称相似而设人工别名确认关卡。

目录停用与历史撤权分开：关店不抹掉历史访问，必要历史补录可由 admin 明确办理并记录理由。有独立稳定 ID 的类别/维度项不复用 ID 或硬删已有引用。门店以名称作业务身份，更名不能自动套用“只改显示名称、旧授权不变”；如需迁移资料和授权，应显式定义并执行，不自动合并。

旧企业按“准备、admin 明确确认、按企业原子启用”切换；准备期仍明确使用旧模型，启用后所有读取入口仅使用新模型，不做旧/新任一通过即放行。保留原始资料，不以此次设计授权删除、回填或发布。固定类别初始密级不能擅自从不同批次上传密级推导；普通文档属性须明确补齐；结构化原件权限从已解析数据自动得出。

切换使旧查询游标失效；旧下载任务若无法证明提交时完整授权清单，标明需重建而不是按旧模型放行。可证明清单的任务按第 6 节执行，不追溯撤回既有签发链接。技术回退须保留新授权边界，做不到则暂停受影响读取，不能自动恢复被撤销权限。

## 9. 实现职责与发布边界

当前实现分工：domain 定义统一读取判定，db 持久化类别/grant/完整范围与版本，API 在查询/状态/签链等入口使用当前权限，worker 区分内部制作与员工读取，launcher/MCP 只做受控适配。公开字段和错误见 [API 契约](api-contract.md)。

当前读取以本文为准，ADR 保留决策历史。经营分区的存储及不保留来源文件边界见 [分区契约](structured-partitions.md)。

launcher 运行时/工具契约变更同批升版本与对齐测试，先发布并独立验证再更新推荐版本和双归属 Skill pin。服务部署、真实资料补齐和企业启用按各自授权边界执行。

## 10. 验证要点

测试采用小型合成资料，覆盖代表性公共路径与边界，不为本次设计建立全组合测试矩阵。

| 场景                                   | 必须成立的结果                                                           |
| -------------------------------------- | ------------------------------------------------------------------------ |
| 同级账号跨企业或缺类别/门店授权        | 不返回业务内容；admin 管理也不能跨企业                                   |
| 类别和范围分属不同授权                 | 不能拼成额外权限；不同实际范围可由各自完整授权覆盖                       |
| 会员在 B 开卡、A 储值                  | 集团级会员授权且密级足够即可读取，无需 A/B 门店权限；原件同规则          |
| 保留原件只解析 A、剩余未识别           | A 全部条件足够即可下载整份；无额外人工声明                               |
| 保留原件解析 A/B、调用人只有 A         | 可读获准 A 数据，不能下载完整原件                                        |
| 类别密级修改或 evidence 重分类         | 新旧相关资料及下一次原件/片段读取使用当前条件，不沿用旧缓存              |
| 只有 PDF 类别权限                      | 能读本店成品，不因此读上游原件；照片提密不影响 PDF                       |
| 照片撤下或替换                         | 旧 PDF 不再签新链接，每日巡检按有效照片重做，既有链接保留 TTL            |
| 打包提交后第 2 分钟撤权、第 5 分钟完成 | 仅权限变化不使制作失败；本人能看进度，领取新链接时拒绝，任务状态仍为完成 |
| admin 无相应正文权但查看员工权限       | 可查看本企业任意账号完整配置并修改，不能借此直接读正文                   |
| 普通 employee 是历史上传者             | 无已发布资料归档权；仅允许清理自己的未完成上传                           |
| 新必需维度启用、旧资料缺项             | 相关读取拒绝，不能通过原件或旧客户端绕过                                 |

实施阶段先运行对应功能的聚焦测试，再在最终代码树运行仓库要求的质量门禁；不因本设计额外执行全套官方人工验收、真实数据回填或大型本地基准。没有部署授权前，不改变线上账号或资料权限。

## 店铺评价的授权边界

`store_reviews` 是独立固定门店级类别，初始密级 null、无默认 grant，不自动变更租户模式或旧类别授权。当前有效同组织 admin 可以写结构化评价；每条资源为一个明确企业和一家精确门店。读取必须由单条完整 grant 覆盖类别、企业、门店及必需维度，并满足当前类别密级；admin 没有普通读取旁路，不拼接多条 grant。
企业候选只来自明确登记的 `BusinessEnterpriseIdentity`，在同一实时权限事务生成完整 write/read 清单并放入权限名片。write 体现当前管理资格和写入配置，read 体现完整授权与密级；不能从评价内容或历史 key 猜显示名。同名门店跨企业分离，评价身份按精确门店/用户及规范化北京时间识别。
launcher `0.14.0` 已发布并独立验证，是当前批准安装 pin；服务发布、类别配置和企业激活仍分别确认。详见 [API 契约](api-contract.md#store-reviews-launcher-0110)。
