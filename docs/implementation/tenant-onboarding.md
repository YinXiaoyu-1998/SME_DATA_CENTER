# 企业入驻与账号授权流程

目标用户入口为“企业专属固定入口＋共享网页登录状态＋服务端严格校验企业身份”，页面体验与登录／密码页一致，默认中文并支持 English。开发者开通企业与管理员后，把企业专属固定 URL 发给管理员；管理员本人在 UI 维护业务规则，不需要填写 JSON。

**当前状态：权限 UI 已在本分支实现并完成本地验证，尚未部署上线。** 路径是官方服务同源 `/admin/permissions/:orgId`，不能提前作为可用链接交付；上线要求和实现边界见[正式设计](admin-permissions-ui-design.md)。本流程不声称已改线上租户模式。

## 入驻次序

1. **运维核对身份并开户。** 核对组织与业务企业身份，通过批准的流程建立组织及首位管理员；auth:operator onboard 只接受已有 Organization.id，不创建组织。QA 的 default-org 不能默认分配给真实客户。账号创建、角色与密码仍由运维负责。
2. **本人建立密码。** 按[受控开户手册](beta-user-onboarding-runbook.md#create-the-beta-account)私下交付一次性浏览器设置链接。本人在第一方页面设密码；不把链接或密码写进仓库、PR、内部 JSON 或 agent 可读文件。
3. **分享固定管理入口。** UI 上线并验证后，由开发者把正式管理 URL 发给企业管理员。它可收藏，本身不授予权限，也不需要像密码设置链接那样每次签发。官方设备网页登录成功后，同一浏览器／用户配置在 30 分钟绝对有效期内无需重复登录；Agent 保持登录不等于浏览器会话仍有效。换浏览器、无痕或过期需重新登录。
4. **管理员在 UI 配置。** 选择八类密级、精确门店、已有支持的业务条件及各账号的密级／读取范围；普通文档逐份设置类别与完整范围。新企业走首次设置，已有企业新增账号复用现有企业规则。
5. **检查并单独启用。** UI 展示准备缺项、具体变更和影响。新企业准备 ready 后由当前管理员明确确认启用；有历史资料则先另行批准并完成补齐。新空企业可先启用再上传真实数据。已有 enabled 企业新增账号不重新激活。
6. **最小交付核对。** 员工通过官方 launcher 登录、查看本人权限卡，在批准范围内验证允许与预期拒绝的读取。无真实资料时只声明配置就绪，不把空结果或登录成功当成业务验收。全套官方人工验收需单独请求。

## 交付检查

- 管理页面、登录及异常提示默认中文、可切换 English；用户明确偏好得到保留，不依赖浏览器语言把首次默认改为英文。
- 企业／账号由当前服务端身份确定；固定类别用已有持久 ID，名称和门店不做模糊合并，角色在权限 UI 只读。
- 0–3 级与显式业务授权同时满足；管理员普通读取也要授权；原始配送台账保持内部材料。
- “全部门店”包含未来新增门店，集团级不是全部门店的别名；账号修改不丢其他既有 grant。
- 保存与激活分离：legacy／preparing 继续旧读取规则，enabled 才执行新规则，suspended 不恢复 legacy。
- 历史来源关系缺项单列，不从可见数据猜测，也不把入驻附带当成部署、回填或启用授权。

## 过渡期与内部格式

UI 上线前，实际管理仍由获准管理员使用[现有 MCP 管理工具](../../skills/smedc-mcp/references/business-authorization.md#admin-tools)，先读当前配置与版本、核对具体差异，再执行获准操作；不把手填 JSON 作为用户门槛。

双归属 Skill 分发[入口约定](../../skills/smedc-mcp/references/tenant-onboarding.md)，默认引导 UI 并明确上线状态；只有开发／运维或 agent 明确需要内部记录时，才使用[内部 JSON 模板](../../skills/smedc-mcp/assets/tenant-onboarding.template.json)及其[字段约定](../../skills/smedc-mcp/references/tenant-onboarding-json.md)。该格式不是公开批量导入／导出合同。

仅空白内部模板进入版本控制。真实企业填写结果、账号标识、目录快照、客户资料和回填清单留在受控私有位置，不进入仓库、Skill、PR 或公开日志；凭据与一次性设置链接完全不进入记录。
