# Skills Shop 设计文档（技能商店）

本文档记录企业资料中枢「技能商店」功能的全部设计决策。会话使用 grill-with-docs 方法进行，
决策一旦确认即写入本文档并同步 `docs/context/CONTEXT.md`；需要时以 ADR 记录难以逆转的边界。

## 定位

技能商店是**企业资料中枢**的技能分发与上传（维护）功能：员工智能体在这里发现、下载已审核的
业务技能包，并在自己本地安装；维护者在这里上传、审核和维护技能包。技能商店托管技能包本体，
但不执行技能内容，也不自动升级员工本地技能。

## 已确认决策

### D-001 分发对象：托管技能包本体（不是外部链接目录）

**决策**：技能商店托管技能包文件本身（简单技能为单个 `SKILL.md`，复杂技能为完整目录结构），
保存于现有文件对象存储（local/OSS），并向外提供确定性、版本化的下载与安装说明。不采用
「只登记元数据 + 指向外部仓库」的模式。

**理由**：需求包含「上传」和「复杂文件结构」；托管本体让员工智能体从统一入口拿到已审核、
固定版本的内容，避免外部仓库内容变动导致的不确定性，也与现有 OSS 存储底座（逻辑 key、
SHA-256、50 MiB 上限）一致。

**边界（保留）**：

- 技能商店不执行技能包里的脚本/代码；
- 技能商店不自动升级员工本地已安装技能；升级由员工智能体/员工根据获取入口信息决定；
- 权限、审计、权威元数据仍由后端强制执行。

**被否决选项**：只登记元数据 + 外部 GitHub 等仓库链接（内容不受控、无法保证版本确定性）。

### D-002 上传单元：单个 `SKILL.md` 或 ZIP，原子创建技能包版本

**决策**：维护者上传简单 skill 时可以直接提交单个、规范命名的 `SKILL.md`；上传复杂 skill 时
提交一个保留完整相对目录结构的 ZIP。服务端将两种输入统一标准化为一个不可变的**技能包版本**，
一次上传必须整体成功或整体失败，第一版不提供逐文件增量上传，也不从 Git 仓库拉取内容。

**理由**：单文件入口保持简单 skill 的低维护成本；ZIP 能原子承载 `agents/`、`references/`、
`scripts/`、`tests/` 等复杂目录。统一标准化后，审核、校验、散列、存储和下载都只需处理一种
内部包版本语义，不会产生只上传了一部分文件的技能包。Git 拉取会额外引入仓库凭证、网络失败、
分支漂移、子模块和供应链信任边界，不进入第一版。

**失败语义**：ZIP 中任一必要文件、路径或内容未通过校验时，整个上传失败，不创建可审核或可分发的
半成品技能包版本。

**被否决选项**：逐文件增量上传（无法天然保证包级原子性）；第一版 Git 导入（扩大认证、网络和
可复现性边界）。Git 导入以后可以作为独立输入适配器设计，但不能改变内部技能包版本语义。

### D-003 包根目录：标准化为唯一根级 `SKILL.md`

**决策**：复杂 skill ZIP 可以将文件直接放在归档根目录，也可以把全部技能包内容放在唯一一层
包装目录中。服务端在校验时自动剥离这层包装目录；标准化后的技能包根目录必须存在且只存在一个
`SKILL.md`。服务端不递归猜测多层目录中的入口。若包装目录外还有其他有效文件、存在多个候选入口，
或无法得到唯一技能包根目录，则整个上传失败。

**标准化示例**：`SKILL.md` + `scripts/run.py`，以及
`smedc-business-analysis/SKILL.md` + `smedc-business-analysis/scripts/run.py`，标准化后表达同一种包结构。
`archive/repo/skill/SKILL.md` 不会被递归识别为入口。

**技术可行性**：现有代码已经使用 `yauzl` 流式读取 XLSX ZIP 中央目录，并实现了不安全路径、
条目数、声明/实际解压大小、压缩比和重复关键条目等门禁。技能包实现可以复用同一类有界扫描模式，
先收集并校验归档内路径，再确定是否剥离唯一公共根目录；不需要先把不可信 ZIP 解压到文件系统。
现有实现不是通用技能包标准化器，落地时仍需新增独立模块、限制配置和恶意归档测试。

**被否决选项**：要求维护者只能制作无包装目录 ZIP（对常见目录压缩操作不友好）；递归寻找任意
层级 `SKILL.md`（入口含糊，可能把包含多个 skill 的仓库误当成单一技能包）。

### D-004 Skill 身份：`SKILL.md.name` 是组织内不可变的 Skill Key

**决策**：标准化后根目录 `SKILL.md` 的 YAML frontmatter 必须包含 `name` 和 `description`。
其中 `name` 是该组织内稳定且唯一的 **Skill Key**，采用小写 kebab-case；创建业务 Skill 后不可
原地改名。为既有业务 Skill 上传新版本时，包内 `SKILL.md.name` 必须与目标 Skill Key 完全一致，
否则整个上传失败。

`description` 描述具体技能包版本，可以随版本变化。`agents/openai.yaml` 等客户端专用元数据中的
`display_name` 只用于展示，不参与身份判断。版本号不拼接到 Skill Key 中，也不由展示名称推导。

**身份作用域**：Skill Key 在组织内唯一；相同文本的 Skill Key 在不同组织中不表示共享身份或
共享权限。当前虽为单企业部署，数据和约束仍保留组织作用域。

**理由**：`SKILL.md.name` 是各客户端能够随包读取的稳定机器标识。以它作为权威身份可以避免上传
表单、数据库名称和实际安装后的调用名称相互漂移；展示文案仍可独立本地化或调整。

**被否决选项**：使用上传文件名或 ZIP 包装目录名作为身份（容易随压缩方式变化）；使用
`display_name` 作为身份（可本地化、包含空格且会调整）；允许新版本改变 `name`（会把升级伪装成
原地改名，并破坏已安装调用方式）。

### D-005 版本输入：可显式指定，也可由服务端自动演进 patch 版本

**决策**：维护者可以在上传请求中显式提供版本号，也可以省略。所有版本号统一使用严格的
`X.Y.Z` 三段数字格式。省略版本号时，企业资料中枢根据该业务 Skill 已保留的版本，在服务端原子
分配下一个版本；默认只演进最后一位，即 patch 位。版本号不要求写入 `SKILL.md`，数据库中的版本
元数据是技能商店的权威版本记录。

**服务端权威性**：客户端或员工智能体不能先读取“当前最高版本”再自行假定下一个版本，因为两个
并发上传者可能计算出相同结果。自动分配必须与版本记录创建处于同一个数据库并发控制边界，最终
采用服务端返回的已分配版本。

**Agent 指导要求**：技能包上传能力上线时，repo-local 与 standalone `smedc-mcp` skill
必须同步加入简短指导：用户明确给出版本时原样提交；用户未给出时省略版本字段、让服务端自动分配
下一个 patch 版本，并向用户报告服务端实际返回的版本。功能实现前不得把尚不可用的上传指导写入
现行 employee skill。

**仍待本决策下一步确认**：新建业务 Skill 省略版本时的初始版本；显式版本是否必须严格大于所有
历史已保留版本；无显式版本重试时如何避免重复演进。

- 推荐版本和弃用语义
