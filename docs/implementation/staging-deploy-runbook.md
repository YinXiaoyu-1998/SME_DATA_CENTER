## Scope

- API and worker run as long-running, lean compiled Docker images on the
  Alibaba Cloud Simple Application Server. They contain only the production
  dependency closure for their service.
- `release-ops` is a separate lean compiled image used only by the on-demand
  Compose `release` profile. It is not a long-running service: deploy invokes
  it for Qdrant initialization, Prisma migration, and the fixture smoke, then
  removes the container.
- Qdrant runs as a Docker container with a local Docker volume.
- MySQL is Alibaba Cloud RDS, not a local container.
- Images are pulled from an account-owned Beijing ACR private registry with
  immutable git-SHA tags.
- nginx publicly exposes `api.smedatacenter.xyz`; `/readyz` remains local-only.

## Trusted Request-Forwarding Topology

The public path is `client -> nginx -> API` on the staging host. nginx overwrites
`X-Forwarded-For` with its direct peer using `proxy_set_header X-Forwarded-For $remote_addr;`; it
does not append caller-supplied forwarding values. The API trusts forwarding metadata only from its
loopback nginx peer (`127.0.0.1`, `::1`, or IPv4-mapped loopback), never through `trustProxy: true`.
This preserves the one-hop public client IP for audit provenance and prevents direct callers from
forging it. Adding a CDN or load balancer requires an explicit reviewed trusted-proxy list and
matching forwarding-boundary tests before that topology is enabled.

## Repeatable deployment

The normal staging release is now one command:

```bash
npm run deploy:staging
```

Prerequisites on the operator machine:

- a clean git worktree so the 12-character git-SHA tag exactly describes the image;
- Node/npm dependencies, Docker Desktop with Buildx, and Trivy (`brew install trivy` on macOS);
- the approved SSH private key outside the repo;
- ACR password in macOS Keychain service
  `com.sme_data_center.acr.personal.smedc` for account
  `nick2373262573`;
- staging cursor-signing secret in macOS Keychain service
  `com.sme_data_center.cursor.staging` for account `smedc-staging`; the GitHub workflow
  receives the equivalent value only through Environment secret `STAGING_CURSOR_SIGNING_SECRET`.

The command performs these gates in order:

1. Refuse a dirty worktree and choose the current 12-character git SHA.
2. Verify the committed staging SSH host key with strict host checking.
3. Log in to ACR with password-stdin, build linux/amd64 API, worker, and
   release-ops images, and push immutable tags. The release-ops sibling tag is
   `ops-<12-character-git-sha>` in the existing API repository.
4. Scan all three images with Trivy and enforce the dependency risk policy.
   Any high or critical finding, or any moderate finding that is not explicitly
   registered, blocks CI and the release before server changes. The sole
   registered ExcelJS read-only XLSX exception must be reviewed by
   `2027-01-31`.
5. Install the cursor-signing secret through stdin, upload and validate Compose, preserve the
   previous Compose/image release, and atomically update only the cursor and API/worker/release-ops
   image variables in the existing root-only `runtime.env`. Other runtime secrets are never rewritten.
6. Pull images, start Qdrant, use the ephemeral `release-ops` profile to
   initialize its collection and run `prisma migrate deploy`, then recreate
   API/worker.
7. Verify server-loopback `/healthz` and `/readyz`, public HTTPS `/healthz`, and
   public `/readyz` returning `404`.
8. Run the fixture-only upload/index/search smoke with a short-lived official synthetic session,
   revoke that session, then record `current-release.env`.

Any rollout/readiness failure after the remote image switch restores the
previous API, worker, and release-ops image references plus the Compose
definition. A public or smoke failure also triggers the same rollback. Prisma
migrations are forward-only and are never reversed by an image rollback, so
all online migrations must remain backward-compatible with the prior image.

Useful modes:

```bash
# Inspect the resolved target and tag without Docker, SSH, or cloud changes.
npm run deploy:staging -- --dry-run

# Redeploy a previously built immutable tag without running a migration/smoke.
npm run deploy:staging -- --tag <git-sha> --skip-build --skip-migrate --skip-smoke

# Show every supported option.
npm run deploy:staging -- --help
```

`--skip-build` still scans the selected ACR images. The smoke command generates
a temporary synthetic admin bearer token locally and must not print or persist
that token.

## GitHub Actions staging delivery

`.github/workflows/staging-deploy.yml` reuses the same release command rather
than maintaining a second deployment implementation.

The automatic path is:

1. A PR is merged to `main`.
2. `Phase 3 quality gates` runs against the trusted `main` merge commit.
3. A successful `push` run triggers `Deploy staging` for that exact commit SHA.
4. GitHub serializes the job with concurrency group
   `smedc-staging`; queued releases are not cancelled.
5. The job installs pinned build/scan tooling and runs
   `npm run deploy:staging`.
6. GitHub records the staging deployment and the release command performs its
   existing migration, health/readiness, fixture-smoke, and rollback behavior.

The workflow also supports manual `deploy` and `rollback` operations through
GitHub Actions, but only when dispatched from `main`. Pull requests and feature
branches cannot enter the deployment job. A `main` push containing only
Markdown or files under `docs/` skips the post-merge quality/deploy chain.

GitHub Environment `staging` contains these secrets:

- `ACR_PASSWORD`
- `STAGING_CURSOR_SIGNING_SECRET`
- `STAGING_SSH_PRIVATE_KEY`

`STAGING_SSH_PRIVATE_KEY` is a dedicated non-interactive CI deployment key, not
an operator's personal encrypted key. Its public key is installed on the
staging host with OpenSSH `restrict`; rotate or revoke that one authorized-key
entry without changing an operator's SSH access.

It contains these non-secret variables:

- `ACR_REGISTRY`
- `ACR_NAMESPACE`
- `ACR_USERNAME`
- `STAGING_HOST`
- `STAGING_SSH_USER`
- `STAGING_PUBLIC_URL`

The repository's current private-plan environment supports Environment secrets
but not additional deployment branch protection rules. The workflow therefore
enforces trusted `main` events itself, uses read-only repository permissions,
pins every third-party Action to a full commit SHA, and removes the temporary
SSH key in an `always()` cleanup step.

The local command remains the recovery fallback when GitHub Actions itself is
unavailable. Do not duplicate release logic in inline workflow shell.

## One-time bootstrap only

`deploy:staging` intentionally does not create or replace `runtime.env`, seed
the database, mirror Qdrant, configure nginx, or issue TLS certificates. Those
one-time bootstrap steps were completed for the current staging host. If the
host is rebuilt, follow the original provisioning/readiness records, recreate
the root-only runtime env, mirror `qdrant:v1.15.4`, run the synthetic seed, and
restore nginx/certbot before using the repeatable release command.

## Structured-import async one-time cutover

This is a single direct staging switch, not a parallel or canary upload path. Merge the complete
backward-compatible migration and async-import PR to `main`, then let the canonical GitHub Actions
staging workflow deploy that exact `main` commit. Do not deploy a PR branch and do not use a local
release command except for an explicitly approved recovery or workflow diagnosis.

After the deployed API and worker have passed their normal health/readiness checks, briefly stop
the API and worker so no upload, retry, or indexing work races the cleanup. Keep Qdrant and RDS
available to the operator. Restore the API and worker immediately after the one-time cleanup, then
rerun health/readiness checks before accepting new uploads.

Use the explicit operator boundary (the `staging:cleanup-upload-domain` operator CLI ships compiled
as `dist/release/staging-upload-domain-cleanup.js` in the release-ops image) only from the quiesced
staging release-operations environment. The support module alone performs no cleanup: the CLI
constructs the repo-contained staging adapter from the live runtime environment. That adapter
enumerates the exact database inventory, exact OSS keys, and exact Qdrant collection/point IDs, then
performs only the injected scoped DB/OSS/Qdrant operations. It fails closed when `DATABASE_URL` or
`QDRANT_URL` is absent, malformed, or local; loopback Qdrant (the real host-network staging shape)
is accepted only when the paired `DATABASE_URL` provably targets the known staging private RDS. The
CLI defaults to dry-run and refuses any target other than `--target staging`; execution additionally
requires `--execute --confirm delete-upload-domain`. Review the dry-run's non-sensitive counts and
IDs before the explicit execution invocation:

```bash
docker compose --profile release --env-file /opt/smedc/runtime.env \
  -f /opt/smedc/docker-compose.yml run -T --rm release-ops \
  node dist/release/staging-upload-domain-cleanup.js --target staging

docker compose --profile release --env-file /opt/smedc/runtime.env \
  -f /opt/smedc/docker-compose.yml run -T --rm release-ops \
  node dist/release/staging-upload-domain-cleanup.js \
  --execute --target staging --confirm delete-upload-domain
```

The local `npm run staging:cleanup-upload-domain` name remains the source entrypoint for tests and
local dry-runs; it must never be pointed at staging from a machine whose runtime env is not the
quiesced staging release-ops environment. The CLI logs only the plan's safe counts/IDs and
post-clean counts; it deliberately excludes DSNs, credentials, file contents, and OSS object keys.
Do not reuse `npm run purge-data`: it remains local-only and must continue refusing non-local
database hosts.

Delete only the enumerated upload domain, never a key prefix or a whole collection:

- each `Document` and its `ProcessingRun, DocumentChunk, DocumentIndex` dependents;
- each related `ImportBatch, ImportWindowClaim, DishRow, and BusinessRow` record;
- each `QuarantineCertificate` that directly references a deleted source document;
- upload audit events whose target/action belongs to the exact document/import identifiers;
- the exact OSS object keys recorded by those `Document` rows; and
- the exact Qdrant collection/point identifiers recorded by those `DocumentChunk` rows.

Post-clean verification must report zero remaining upload-domain documents, processing runs,
chunks, indexes, import batches, import-window claims, dish rows, business rows,
related upload audit events, enumerated OSS objects, and enumerated Qdrant points. It must preserve
Organization, Employee, login identity and authorization records, SkillEntry, RetrievalConfig,
and auth audit records.

Complete `npm run test:official-manual` only after services are restored. The official acceptance
must use a fresh synthetic account and show a valid table reaching `applied`, an invalid table
reaching `rejected`, an evidence text upload reaching `ready`, and hard deletion of all acceptance
account/test data afterward.

## Manual rollback

The release command records the last API/worker/release-ops image references
and Compose release before switching.
Restore it and rerun readiness plus fixture smoke with:

```bash
npm run deploy:staging:rollback
```

For an older known tag rather than the immediately previous release, use the
`--tag ... --skip-build --skip-migrate` form above. Image rollback does not reverse Prisma
migrations: migrations are forward-only, so the prior image must remain compatible with every
already-applied migration.

Do not delete the Qdrant volume or RDS data during a routine image rollback.
