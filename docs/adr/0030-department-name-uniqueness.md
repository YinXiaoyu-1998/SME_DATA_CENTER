# 部门名称在同一业务企业内唯一

2026-11-11 已确认设计，尚未实现。完整规格为 [Issue #337](https://github.com/YinXiaoyu-1998/SME_DATA_CENTER/issues/337)，实施边界见[菜品目录当前状态实施计划](../implementation/dish-catalog-current-state.md)。

## 决定

- `(org_id, enterprise_key, name)` 在 `business_departments` **全状态唯一**，包含已停用部门。停用后名称不复用；需要重新启用时使用既有 `restore` 操作。
- 创建与重命名都在员工目录写入事务内校验。该事务已对业务企业身份行加 `FOR UPDATE`，同一企业的目录写入天然串行，查重与写入之间没有竞态；数据库唯一索引作为最后防线。
- 名称保留首尾空白时拒绝创建或重命名，不静默 trim。目录读取和菜品目录的部门解析都使用精确字符串相等，不做大小写、全半角或空白归一化（实际比较沿用列排序规则）。
- 冲突返回 `DIRECTORY_DUPLICATE_NAME`（HTTP 409）。HTTP、MCP 与前端使用同一错误码。
- 前端在部门创建和重命名表单做同样的本地校验，并把服务端冲突映射到名称字段的行内错误；后端始终是权威判定。

## 理由

菜品目录写入按部门名称解析为稳定部门标识，名称歧义会让解析失准；部门目录本身也不该出现两行同名记录。目录侧只做防御性拒绝，不承担去重职责：唯一性必须在部门目录的写入口保证，且不能只靠应用层检查——任何绕过服务的写入都应被数据库拒绝。全状态唯一避免同名两行（一停一用）同时出现在列表和匹配结果里；既然已有 `restore`，停用名称不能被复用并不影响恢复。

## Considered Options

- 仅服务层检查：现有行锁已能保证并发正确，但缺少库级不变量。
- 仅未停用唯一：会出现同名两行，历史员工和目录解析都可能指向不同记录。
- 静默 trim：改写管理员输入，且与门店名称不 trim 的现状不一致。
- 目录写入侧自行去重：把目录不变量推给每一个消费方。

## Consequences

- 迁移前必须预检现有重复部门并人工处理（重指向员工或改名），迁移不得静默改数据；有重复时迁移直接失败。
- 已停用名称不可复用；确需复用时先重命名已停用的旧部门。
- 跨仓改动：`web-api-contract` 错误码联合类型、`SMEDC_FRONTEND` 表单校验与契约再生成。
