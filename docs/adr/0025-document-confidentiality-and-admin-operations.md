# 资料密级与管理员特权操作

企业资料中枢以“组织边界 + 0–3 资料密级”取代员工、门店、个人和全员标签的资料访问模型。每个账户在开发者创建时必须明确提供 `admin` 或 `employee` 角色以及 0–3 保密等级；每份资料必须有 0–3 密级，上传未明确提供时为 0。普通员工侧读取始终先限于同组织，再要求账户保密等级不低于资料密级，并对正文、元数据、检索、结构化行和聚合统一生效。`admin` 是功能身份而非普通读取豁免：任何检查 admin 的功能即为显式的 Privileged Administrative Operation，所有 admin 均可在该功能的既定范围内无视目标密级（包括该功能定义的读取），但这不会扩大其他普通读取接口的范围。

## Consequences

- 不再存在标签、标签目录、员工标签、资料标签、门店/个人/全员标签，或任何兼容与迁移语义；旧标签及关联数据可以清空。
- 服务内部直接从资料产生的分块、索引、结构化行、聚合、元数据视图和下载能力继承来源资料密级。员工或 agent 在服务外产生后再次上传的文件是独立新资料；服务不追踪或推断其来源链路，agent 也不得从文件名、内容或业务上下文自行升密。
- 密级在上传后不提供员工侧或 admin 侧重定级功能；账户保密等级也不提供应用内修改功能。两者仅由开发/DevOps 运维处理，账户保密等级只在开户时明确给定。
- 禁用账户在禁用期间没有任何员工侧能力，包括 admin 特权功能；历史记录保留并可由 DevOps 日后重新启用。
- 实施时一次性映射现有 `admin` 为 `admin`、`manager` 为 `admin`、`employee` 为 `employee`；现有账户设为 3 级、现有资料设为 0 级。当前 staging 资料均视为 QA 测试数据。

## Considered Options

- 保留门店、个人和全员标签并继续以标签交集授权；拒绝，因为门店和人员是业务信息，不是资料访问边界。
- 将 admin 自动视为最高密级；拒绝，因为功能身份与普通资料读取权限应正交。
- 为员工或 agent 自动从文件内容、文件名或外部来源推断密级；拒绝，因为资料密级是上传时的明确用户输入，不是中枢的推断职责。
- 为旧数据和旧标签保留兼容层；拒绝，因为旧数据可以直接清空，双模型只会扩大复杂度。
