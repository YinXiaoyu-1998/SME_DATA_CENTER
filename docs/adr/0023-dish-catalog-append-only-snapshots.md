# 菜品目录采用单时间线的追加式完整快照

`dish_catalog` 与按业务日期窗口导入的经营数据不同：每个企业只有一条菜品目录时间线，每次上传都以单一 `snapshotDate` 声明一份完整目录快照。同一日期只能有一份有效快照，但允许乱序补录历史日期；所有快照行追加到同一张表，历史快照默认保持可查询且不因新快照自动归档。这个模型用可接受的重复行换取原始快照完整还原、批次原子性、来源追溯和简单可靠的写入语义，拒绝在导入阶段采用 SCD、增量合并、原地覆盖或跨快照业务状态推断。

一个快照可以合并多个表头严格匹配的可见 sheet，sheet 名称不参与识别；不匹配 sheet 被忽略并记录安全摘要，隐藏且匹配的 sheet 使导入失败。目录行以 SKUID 标识并在单个快照内唯一，SPUID 允许因多规格重复。服务通过现有 discovery 和受控结构化查询暴露 `snapshot_date` 与目录字段，但不选择当前目录、不推断新增/删除/下架，也不生成快照 diff。

**Considered Options**: 为每次上传创建独立表；只保存相邻快照差异；使用 SCD 有效期版本；新快照自动归档旧快照；在导入时推断菜品状态；要求所有非空 sheet 都匹配目录 schema。

**Consequences**: 菜品数量和菜单变更频率较低，因此跨快照重复保存未变化 SKU 的存储成本可接受。调用方需要显式按 `snapshot_date` 选择或比较快照；未来若增加 current/diff 能力，必须保持历史快照、权限过滤、归档和批次血缘语义。
