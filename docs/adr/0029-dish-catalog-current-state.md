# 菜品目录改为当前状态，由批量 MCP 接口维护

2026-11-11 已确认设计，尚未实现。取代 [ADR 0023](0023-dish-catalog-append-only-snapshots.md) 的追加式快照模型；完整规格为 [Issue #337](https://github.com/YinXiaoyu-1998/SME_DATA_CENTER/issues/337)，实施边界见[菜品目录当前状态实施计划](../implementation/dish-catalog-current-state.md)。

## 决定

- 每个业务企业一份**当前**菜品目录：`(org_id, enterprise_key, sku_id)` 唯一，一行一个 SKU。不再有按日期的快照时间线、`snapshot_date` 元数据或跨快照状态推断。
- 唯一写入路径是管理员调用 `upsert_dish_catalog`（HTTP `POST /v1/dish-catalog/upsert`）：提交 `rows[]` 与可选 `removeSkuIds[]`，两者合计最多 1000，整批原子成功或整批失败。**不接受文件上传**，文件解析留在调用方智能体的本地环境。
- 行字段是权威值：必填字段必须出现；可空字段省略即清空；不 trim、不四舍五入、不把“没传”解释为“保持原值”，也不推断新增、删除或下架状态。
- 部门归属存**稳定部门标识** `department_id`，可空。写入接受部门名称，服务端在该业务企业的未停用部门中精确解析为 ID；读取按 ID 关联部门目录返回当前名称。部门改名不改写目录行，也不存在名称失配或错绑；不自动创建部门。
- 目录行**不继承源文档权限**，但沿用同一套授权模型：每业务企业一份目录资源（类别 `dish_catalog`、集团级 scope），首次写入时创建；读取仍走 `business_resources`/scope/grant 谓词，只把关联锚点从源文档换为企业。没有资源或未启用授权时失败关闭（无行）。
- 批次只写真实变化：`created_at` 仅插入时写，`updated_at` 仅内容实际变化时刷新；无变化的重放不触碰时间戳。不维护目录级 `revision`，不加状态表。
- 每批只记录一条审计（操作人、`request_id`、企业、计数、可选来源文件名），不记录行级明细；删除与覆盖不可恢复。
- 查询继续走受控结构化查询；字段去掉 `snapshot_date`，新增 `department_id`、`department_name`、`created_at`、`updated_at`；coverage 由快照列表改为 `{rowCount, lastUpdatedAt}`。
- 硬切：写入面、launcher 上传枚举、目录专用表头/sheet 校验、worker 解析分支一并移除；旧表删除，不做数据迁移、双写或兼容开关。

## 理由

文件解析加快照时间线是为“整份导出、逐日对比”设计的，而真实维护动作是菜品级的增删改。让智能体直接提交结构化行，可以精确表达“新增哪几行、删除哪几行”，避免表头、sheet 合并和空值语义带来的解析差异。部门用稳定 ID 而不是名称，是因为部门会改名；存名称就必须级联、否则旧行会被新部门静默错绑。当前状态模型让“这道菜归哪个部门”成为唯一的行属性，读取时再解析名称，改名天然一致。

## Considered Options

- 保留快照、只把文件换成行：仍然“改一行等于新快照”，与维护动作不匹配。
- `replace` 整份替换：漏传即删除，误删风险不可接受。
- 软删除状态：查询与权限语义复杂化，且没有历史查询需求支撑。
- 行级 `revision`：引入尚未实现的并发语义，容易被误当乐观锁。
- 存部门名称并在改名时级联更新：多一条跨功能写入路径，且任何漏级联或并发窗口都会造成错绑。
- 读取时直接按 grant 拼企业列表、不建资源：绕过既有 resource/scope 授权模型，安全规则出现第二份实现。
- 文件与行混合入口：两套校验、错误和安全边界，违背单一写入路径。

## Consequences

- 不能回答“某历史日期的菜单是什么”。需要历史对比时由调用方在写入前自行留存，服务不提供快照。
- 硬删除不可恢复；审计只记录批次计数，不记录删除的是哪几行。
- 目录资源由写入创建，不再是上传原件的副产物；删除全部行不会删除资源，coverage 保持 0 行状态。
- 删除旧链路触及 launcher 版本边界和双仓 Skill，必须按“服务端 → launcher → Skill”顺序发布。
- 部门改名对读取透明；停用部门仍可被既有行引用并正常显示名称，只影响后续写入。
